# Flow — YouTube video & music downloader

Этап 4: скачивание видео со звуком и отдельного аудио на Next.js и TypeScript.

## Запуск

```sh
npm install
npm run setup:media
npm run dev
```

Открыть http://127.0.0.1:3000. Проверка сборки: `npm run build`.

## Реализовано

- Во время загрузки показываются реальные скорость и примерное время до конца текущей дорожки из yt-dlp. Оценка не включает следующие дорожки, объединение и передачу готового файла в браузер. Неизвестные или устаревшие более чем на 10 секунд значения заменяются на «Уточняем…»; после смены этапа скрываются.
- «Время этапов» показывает длительности проверки, загрузки и обработки; API возвращает их в миллисекундах (`timings`). Загрузка включает повторное получение данных источника самим yt-dlp, не только передачу байтов. Это замеры, не обещание ускорения.

- Последняя созданная задача сохраняется в `sessionStorage` и восстанавливается после обновления той же вкладки без повторного анализа/скачивания. При потере задачи на сервере показывается объяснение. Это не восстановление после перезапуска сервера; серверные задачи пока в памяти.
- DELETE `/api/downloads/:id` отменяет активную задачу. На Windows завершается дерево процессов через `taskkill /T /F`, на Unix — выделенная группа процессов. Отменённая задача не выдаёт файл; временная папка очищается. Повторная отмена безопасна, готовый файл не удаляется.
- Прогресс разделён на проверку, загрузку, обработку и готовность. Процент загрузки усредняется по дорожкам и не откатывается при переходе от видео к аудио; обработка отображается отдельным этапом без выдуманного процента.

- Вкладки видео/аудио, проверка YouTube URL, мобильная навигация и FAQ.
- Явно обозначенный демопример с выбором MP4/WebM и MP3/M4A/WebM.
- Пример качества до 2160p, без утверждения о доступности для введённого URL.

POST `/api/analyze` принимает `{ "url": "https://www.youtube.com/watch?v=..." }` и возвращает название, канал, обложку, длительность и доступные варианты. Отдельный дочерний процесс yt-dlp получает метаданные без скачивания медиа. API подбирает совместимые видео- и аудиопотоки. Исходные медиа-URL клиенту не передаются.

Видео скачивается через задачи: POST `/api/downloads` с `{videoId, optionId}`, GET `/api/downloads/:id` для состояния, GET `/api/downloads/:id/file` для сохранения. Сервер повторно проверяет выбранный формат, загружает точные дорожки и объединяет их FFmpeg без повышения разрешения. Доступны видео MP4/WebM, исходное аудио M4A/WebM и MP3 (128/192/256/320 кбит/с). MP3 преобразуется FFmpeg, увеличение битрейта не повышает качество исходника. Демопример не создаёт задач.

Для Windows выполните `powershell -File scripts/setup-ffmpeg.ps1`: сборка Gyan, указанная на странице загрузки FFmpeg, устанавливается в `.tools` с проверкой SHA256. На других ОС установите FFmpeg и задайте абсолютный `FFMPEG_PATH` в `.env.local`.

Локальные ограничения: две задачи одновременно, до 2 ГБ на готовый файл, до 30 минут на скачивание, хранение один час после завершения. Проценты относятся к этапу загрузки и усредняются по видео- и аудиодорожке. Временные файлы в `.downloads/` исключены из Git; фоновая очистка работает каждую минуту, старые файлы после перезапуска тоже удаляются. Состояния задач хранятся в памяти одного долгоживущего Node.js-процесса и теряются при перезапуске. Для публичного многосерверного/серверлесс-развёртывания нужны отдельный worker, общая очередь, аутентификация задач и общие квоты. Ссылка с непредсказуемым UUID даёт доступ к файлу любому её обладателю в течение срока хранения.

## Установка обработчика и ограничения

Нужен Node.js 24+ (в том числе для запуска тестов TypeScript встроенным загрузчиком). `npm run setup:media` скачивает официальный релиз yt-dlp в игнорируемую `.tools/` и проверяет SHA256 по файлу контрольных сумм этого релиза. Поддержаны Windows x64, macOS и Linux x64; для других архитектур установить подходящий yt-dlp самостоятельно и указать `YTDLP_PATH` в `.env.local`. Повторный запуск команды обновляет обработчик.

Встроенные JS challenge scripts официального бинарника и Node.js используются согласно [документации yt-dlp](https://github.com/yt-dlp/yt-dlp/wiki/EJS). Серверу нужен доступ к YouTube. Cookies и аккаунт пользователя не используются. Публичные и Unlisted-ссылки проходят один путь анализа; фактическая доступность определяется YouTube. Приватные ролики, активные трансляции и запросы с требованием авторизации возвращают ошибку.

Локальный MVP ограничивает тело запроса 4 КБ, время анализа 60 сек., вывод 8 МБ и число параллельных анализов двумя на процесс, включая повторные проверки перед скачиванием. Кэш результатов не создаётся. На хостинге должен быть разрешён запуск бинарников, для Edge runtime это решение не подходит.

Защита ресурсов одного сервера:

- Общий бюджет запросов: 30 анализов и 10 созданий задач в минуту; превышение возвращает 429, понятное сообщение и `Retry-After`. Это общий лимит процесса, не персональная квота пользователя; заголовкам с IP клиента сервер не доверяет.
- Перед созданием задачи последовательно проверяется свободное место: резерв 4 ГиБ на задачу (дорожки + результат), общий бюджет `.downloads` 10 ГиБ и минимум 1 ГиБ свободного места сверх оставшихся резервов.
- Во время обработки каждые 2 секунды проверяется размер папок и диск. Превышение 4 ГиБ на задачу, 10 ГиБ суммарно или остаток менее 512 МиБ останавливает обработчик. Это периодический контроль, не жёсткая файловая квота: между проверками возможно кратковременное превышение.
- Одновременно выдаются не более четырёх файлов, не более двух передач одной задачи.

Лимиты и резервы хранятся в памяти и сбрасываются при перезапуске; существующие файлы учитываются при проверке диска. Для нескольких серверов нужны общие квоты, очередь и изолированный worker — текущая защита не заменяет их.

## Проверки

Проверены мобильные размеры 320 и 390 px: перенос длинного названия, отсутствие горизонтальной прокрутки, карточка скорости/времени, ошибочная ссылка, отмена активной загрузки и повторный запуск. Некорректный URL больше не отображается как подтверждённая ссылка YouTube.

На тестовом Blender 480p: проверка 4,5 сек., загрузка 9,9 сек., обработка 0,5 сек. Предоставленная пользователем Unlisted-ссылка прошла полный цикл без cookies/авторизации: файл 144p со звуком, 1738,27 сек.; проверка 4,0 сек., загрузка 51,5 сек., обработка 0,76 сек. Адрес и название Unlisted не публикуются. Эти отдельные замеры не являются сравнительным бенчмарком и не гарантируют скорость других загрузок.

Для повторной сквозной проверки отдельной ссылки: `node scripts/verify-single-download.mjs "URL"`. Скрипт выбирает небольшой доступный MP4, проверяет полученный файл через ffprobe и сохраняет тестовую копию в `.tools/smoke-download.mp4` (повторный запуск заменяет её).

Проверены восстановление активной Full HD-задачи после обновления страницы, отмена во время скачивания и MP3-конвертации с удалением временных папок, восстановление ссылки на готовый M4A. Тест дерева процессов проверяет завершение дочернего процесса вместе с основным; в ограниченной песочнице ему нужны права управления тестовыми процессами. Восстановление хранит только UUID задачи, а свежий статус получает с сервера.

Аудио проверено сквозным скачиванием на Blender `aqz-KE-bpKQ`: сохранённый M4A содержит только AAC, WebM — только Opus, MP3 — только MP3-аудио с выбранным битрейтом 192 000 бит/с. Проверка выполнена ffprobe после получения файлов через API. Преобразование использует [официальные параметры yt-dlp](https://github.com/yt-dlp/yt-dlp#post-processing-options).

`npm test` проверяет разбор URL, подбор совместимого звука, размеры, фильтрацию DRM и доступные разрешения. `npm run build` проверяет сборку и TypeScript.

При запущенном сервере задайте `FLOW_TEST_URL=http://127.0.0.1:3001` и выполните `npm test` для дополнительных проверок API скачивания: чужой Origin, повреждённый JSON, неподходящие идентификаторы, лимит тела запроса и отсутствующие файлы. Без переменной сетевой тест пропускается.

Сквозная проверка скачивания выполнена на Blender `aqz-KE-bpKQ` в 144p: через интерфейс создана задача, API выдал MP4 размером 14 877 868 байт; ffprobe подтвердил H.264-видео и AAC-аудио, длительность 634,6 секунды.

Также полностью скачаны и получены через API MP4 в 1080p (1920×1080, H.264 + AAC, 268 281 336 байт), 1440p (2560×1440, AV1 + AAC, 323 053 489 байт) и 2160p (3840×2160, AV1 + AAC, 722 944 168 байт). Все три файла: 60 fps, длительность 634,624580 секунды; ffprobe проверил разрешение, наличие звука, длительность и размер полученного файла. Первая попытка 4K завершилась ошибкой обработчика, повторная прошла. Это проверка конкретных вариантов одного ролика, не гарантия доступности любого видео или совместимости AV1 с любым устройством.

Повторить проверку: `node scripts/verify-video-quality.mjs` при запущенном сервере (по умолчанию порт 3001), либо указать разрешение аргументом, например `node scripts/verify-video-quality.mjs 2160`. Скрипт скачивает полные файлы, использует интернет-трафик и сохраняет тестовые копии в игнорируемую `.tools/quality-check`.

При разработке API успешно проанализировал публичный ролик Blender `aqz-KE-bpKQ`: получены реальные 1080p, 1440p, 2160p/60fps и аудиодорожки. Недоступный ролик вернул понятную ошибку 422.

## Следующие этапы

1. Перенести обработчик за очередь при развёртывании.
2. Устойчивость задач к перезапуску сервера и распределённые квоты при масштабировании.
3. Redis/BullMQ, изолированный worker и общее хранилище при публичном развёртывании.
4. Развёртывание после выбора хостинга и согласования эксплуатационных лимитов.

Продуктовые требования: публичные и Unlisted ролики; качество определяется источником; исходные MP4/WebM/M4A, MP3 через конвертацию; без повышения разрешения. MP4 — контейнер, совместимость устройств зависит также от кодека. Доступность выходного формата должна определяться сервером, а не статическим списком демо.

Предлагаемая структура: Next.js UI/API → Redis/BullMQ → изолированный worker (yt-dlp/FFmpeg) → временное файловое хранилище; PostgreSQL для постоянных задач при переходе к production. Перед развёртыванием согласовать лимиты длительности, размера и хранения.
